2.2 RWA Token — SEP-41 + OpenZeppelin Stellar Compliance
Each tokenized asset gets its own SEP-41 compliant token contract, deployed by the Sale Contract via create_asset() . The token
implements the full SEP-41 interface (9 standard functions) extended with OpenZeppelin Stellar compliance modules for regulatory
enforcement.
Compliance Features from OpenZeppelin Stellar
FEATURE OZ MODULE PURPOSE
Allowlist transfers Allowlist Only KYC-verified addresses can send/receive tokens
Blocklist enforcement Blocklist Sanctioned or flagged addresses permanently blocked
Capped supply Capped Total supply = asset valuation / token price, immutable after creation
Pausable Pausable Emergency halt of all transfers by admin

fn mint(e: Env, to: Address, amount: i128) {
    let admin = read_administrator(&e);
    admin.require_auth();
    check_nonnegative_amount(amount);
    "// Enforce supply cap — cannot exceed asset valuation
    let supply = read_total_supply(&e);
    let cap = read_supply_cap(&e);

        panic_with_error!(&e, Error"::SupplyCapExceeded);

    receive_balance(&e, to.clone(), amount);
    write_total_supply(&e, supply + amount);

2.3 Revenue Distribution Engine — Port from EVM
Tokeshare already distributes real USDC revenue on EVM chains via a push-based BatchDistributor  contract ( 0x8c1eCBa""...  on Polygon).
The Soroban version adopts a pull-based architecture — the operator deposits revenue, and holders claim their pro-rata share individually.
This design is significantly better suited to Soroban's resource model (bounded CPU per invocation, no unbounded loops).

fn deposit_revenue(e: Env, operator: Address, asset_id: u64, amount: i128) {
    operator.require_auth();
    require_operator(&e, &operator);
    "// Transfer USDC from operator to contract
    let usdc = token"::TokenClient"::new(&e, &load(&e, &DataKey"::UsdcSac));
    usdc.transfer(&operator, &e.current_contract_address(), &amount);
    "// Snapshot total supply at distribution time
    let rwa = token"::TokenClient"::new(&e, &load_asset_token(&e, asset_id));
    let snapshot = rwa.total_supply();
    "// Record distribution
    let dist_id = increment_counter(&e);
    e.storage().persistent().set(
        &DataKey"::Distribution(dist_id),
        &DistRecord {
            asset_id,
            amount,
            supply_snapshot: snapshot,
            ledger: e.ledger().sequence(),
            timestamp: e.ledger().timestamp(),
        },
    );
    DistEvents"::deposited(&e, dist_id, asset_id, amount);
}
claim()
fn claim(e: Env, holder: Address, dist_id: u64) "-> i128 {
    holder.require_auth();
    let dist = load_distribution(&e, dist_id);
    "// Prevent double-claim
    if e.storage().persistent().has(&DataKey"::Claimed(dist_id, holder.clone())) {
        panic_with_error!(&e, Error"::AlreadyClaimed);
    }
    "// Calculate pro-rata share: (holder_balance * total_revenue) / total_supply
    let balance = token"::TokenClient"::new(
        &e, &load_asset_token(&e, dist.asset_id)
    ).balance(&holder);
    let share = (balance * dist.amount) / dist.supply_snapshot;
    "// Transfer USDC to holder
    let usdc = token"::TokenClient"::new(&e, &load(&e, &DataKey"::UsdcSac));
    usdc.transfer(&e.current_contract_address(), &holder, &share);
    "// Mark as claimed
    e.storage().persistent().set(&DataKey"::Claimed(dist_id, holder.clone()), &true);
    share
}
Safety Guarantees
Supply snapshot — frozen at deposit time, prevents dilution attacks (minting after deposit to claim larger share)
Claimed flag — persistent storage prevents double-claiming across ledger boundaries
Pull-based — no unbounded loops, each claim is O(1), compatible with Soroban resource limits
Operator gating — only authorized operators can deposit, prevents griefing via dust deposits

3. Integration Architecture (8 Integrations)
3.1 Stellar Wallets Kit
Status: Already integrated  |  Package: @creit.tech/stellar-wallets-kit
User clicks "Connect Wallet" → openModal() → wallet selection (Lobstr / Freighter / xBull) → signTransaction() → submit
to Soroban RPC → confirmation
Existing code: lib/stellar.ts  (157 lines), hooks/useTresSale.ts  (80 lines), config/stellar.ts  (33 lines)
Extensions for production: multi-asset browsing across all listed RWAs, automatic trustline management for new RWA tokens,
portfolio dashboard with claim history.
3.2 Privy
Purpose: Onboard non-crypto LATAM users via email/social login with embedded Stellar wallets
User enters email → Privy SDK → embedded Stellar keypair generated → custodial model → signTransaction() via Privy →
submit to Soroban RPC
Dual-path architecture: Crypto-native users connect via Stellar Wallets Kit. Non-crypto users sign up with Privy. Both paths
converge on the same Soroban contracts — the frontend detects which signer is active and routes accordingly.
3.3 MoneyGram Access
Purpose: Cash-in/cash-out for unbanked or cash-preferred LATAM investors  |  Coverage: 400K+ agent locations worldwide
Cash-in: Investor visits MoneyGram agent → deposits local fiat → USDC credited to Stellar wallet → invest in RWA token 
Cash-out: Investor claims USDC revenue → sends USDC to MoneyGram → collects local currency at nearest agent
Integration: KYB registration at T0 → Developer Portal API access → programmatic cash-in/cash-out flows.
3.4 alfredpay
Purpose: Direct bank transfers in LATAM local currencies (DOP, ARS, COP)
Investor requests withdrawal → alfredpay API → USDC converted → DOP/ARS/COP bank transfer → investor's local bank account
Complementary to MoneyGram: MoneyGram handles cash; alfredpay handles bank transfers. Together they cover both banked and
unbanked LATAM populations.
3.5 Stellar Disbursement Platform (SDP)
Purpose: Bulk USDC revenue distribution to all token holders at scale
Operator collects revenue from asset → SDP bulk payment API → USDC distributed to all holder wallets → operator dashboard
for tracking & audit
Scale advantage: SDP is battle-tested by SDF for disbursements to thousands of recipients. Used alongside the pull-based Revenue
Distribution Engine — SDP handles the off-chain orchestration and notification layer while the contract handles on-chain accounting.
3.6 CCTP (Cross-Chain Transfer Protocol)
Purpose: Bridge native USDC from EVM chains (Ethereum, Base, Polygon) to Stellar for investment
Connect EVM wallet → approve USDC spend → TokenMessenger.depositForBurn() on EVM → Circle attestation service →
receiveMessage() on Stellar → native USDC minted on Stellar → invest in RWA token
Frontend UX: Burn confirmation → attestation status polling → mint completion → automatic redirect to asset purchase flow. The user
sees a single unified experience.
Strategic value: Opens Tokeshare to the entire EVM DeFi ecosystem — users with USDC on Ethereum/Base/Polygon can invest
without first manually bridging.
CCTP CROSS-CHAIN FLOW — EVM TO STELLAR
EVM INVESTOR  Approve USDC spend on EVM chain
↓
EVM INVESTOR  Call depositForBurn(amount, stellar_dest)
↓
EVM CHAIN  USDC burned on source chain
↓
CIRCLE  Burn event detected — attestation generated
↓
STELLAR  receiveMessage(attestation) — native USDC minted
↓
SALE CONTRACT  buy(asset_id, amount) — RWA Token delivered to investor
3.7 Soroswap
Purpose: USDC/RWA AMM pools for secondary market liquidity
RWA Token (SEP-41) → Soroswap factory creates USDC/RWA pool → Router API for swaps → swap widget embedded in Tokeshare
frontend → secondary market trading
Native compatibility: All RWA tokens implement SEP-41, making them natively tradeable on Soroswap without any wrapper or
adapter contracts.
3.8 Aquarius
Purpose: Swap routing optimization across Stellar DEXes
Swap request → Aquarius routing engine → optimal path calculated across available DEX liquidity → minimized slippage for
investor
Integration effort: Under 1 day — Aquarius provides a routing API that complements Soroswap. When multiple liquidity sources exist
for a pair, Aquarius finds the best execution path.
