 Objective of the Document The objective of this document is to define the technical architecture and integration flows for Escala, a B2B Fintech-as-a-Service (FaaS) infrastructure. This solution allows corporate clients (NGOs, cooperatives, and platforms like Amero) to embed community collective investment funds within their own applications.
Escala abstracts the complexity of Web3, providing RESTful APIs that orchestrate smart contracts on Soroban (Stellar) for governance (Soulbound Tokens) and treasury management (USDC escrows), connecting natively with fiat rails via our Integration Track partners (MoneyGram and Circle).
This architecture is backed by rigorous institutional validation and real-world execution. The foundational "Collective Investment" primitive of Escala was selected as a global winner at the United Nations Hackathon, following an invitation from the Stellar Development Foundation. Subsequently, our team was selected for the UNDP SDG Blockchain Accelerator, where we successfully graduated as finalists. This extensive acceleration process culminated in a live Demo Day in a municipality in Guatemala, where the entire application ecosystem—including the end-to-end B2C user flows, the Soroban smart contracts (Treasury and Governance), and the fiat-to-crypto integrations—was successfully tested and validated in a real-world community setting.

2. Solution Overview
The platform's operation is based on Stellar blockchain technology and Soroban smart contracts, guaranteeing transparency and automated fund execution.
Instead of operating solely as an end-user app, Escala acts as a multi-tenant middleware. It integrates fiat on/off-ramps, KYC/AML providers, and wallet management with on-chain Soroban contracts. Users of our B2B clients form closed groups with their own governance and finance local projects through proportional contributions.
B2B Cloud Studio & AI (Developer Experience): Escala HQ provides a B2B 'Cloud Studio' for enterprise integration. The AI component is strictly a Developer Tool (DevTool) leveraging the Model Context Protocol (MCP). It assists B2B clients (engineers at NGOs or cooperatives) in generating repetitive configuration code, reducing the time to integrate Stellar primitives (Soroban, SDP, MoneyGram) from months to weeks. 
Multi-layer Governance
	•	Group Governance Token (Non-transferable / SBT): Ensures a democratic voice in general committee elections and community rules.
	•	Project Participation Token (Fungible): Assigned proportionally to the user's USDC contribution. It confers voting power and benefits linked specifically to individual initiatives (e.g., funding a community solar panel).

3. Key Business Flows
3.1. Contribution via Remittances (Embedded Flow)
To facilitate contributions, Escala  provides an API that B2B clients can embed in their checkout flows.
	•	Remittance/Payment Initiation: An end-user initiates a transaction on the client's app (e.g., Amero).
	•	Contribution Prompt: The UI asks: "Do you want to contribute to a community fund project?"
	•	Execution: If accepted, the Escala API routes the fiat through MoneyGram/Circle, converts it to USDC, deposits it into the Soroban TreasuryContract, and mints proportional ProjectTokens to the user's wallet.  
3.2. Milestone-Based Fund Release
	•	Evidence Upload: The fund administrator uploads proof of work (receipts, photos) to the off-chain storage.
	•	Oracle Attestation: An authorized Oracle (e.g., UNDP auditor) validates the evidence and signs an attestation hash.
	•	On-Chain Voting & Release: The VotingContract verifies the quorum and majority. If passed, it triggers the TreasuryContract to release the specified USDC tranche to the vendor or administrator.
	•	Automated Disbursements (via SDP): Once the VotingContract triggers the release from the TreasuryContract, our middleware Event Hub catches the on-chain event and immediately triggers the Stellar Disbursement Platform (SDP) REST API to execute bulk, compliant payouts in USDC to local vendors.

4. Technical Aspects (Smart Contracts on Soroban)
The solution architecture relies on 2 foundational smart contracts deployed on the Stellar network:
	•	TreasuryContract (USDC Escrow): Manages pooled USDC funds. It provides total transparency, allowing any party to audit accumulated balances. Funds are locked and only released upon successful cryptographic triggers from the VotingContract or Oracles.
	•	Core Functions: deposit(), requestDisbursement(), executeDisbursement().
	•	VotingContract (Governance & Delegation): Links voting power to the amount of participation tokens held. It includes liquid democracy features, allowing users to delegate their votes to trusted community members.
	•	Core Functions: createProposal(), castVote(), delegateVote(), tally().
	•	ProjectToken (FT): A fungible token minted upon USDC deposit, representing fractional ownership/contribution to a specific project.
	•	Governance Token (SBT): A Soulbound Token granting baseline membership and governance rights within a broader community fund.
Justification: SBTs are not a marketing feature; they are a strict compliance and governance requirement from our UNDP pilot. In vulnerable communities, voting rights must be strictly non-transferable [1 person = 1 vote] to prevent vote-buying, Sybil attacks, and fund manipulation. Soroban enforces this restriction on-chain

Stellar Ecosystem & Integration Track Specifics
As an Integration Track submission, Escala B2B architecture is explicitly designed around existing Stellar ecosystem primitives. Our middleware orchestrates the following building blocks:
A. Core Stellar Integration (Soroban Smart Contracts) The core logic for fund custody and governance runs entirely on Soroban (Stellar) :
	•	TreasuryContract (USDC Escrow): Written in Rust and deployed on Soroban, this contract holds the pooled USDC . It enforces multi-signature requirements and timelocks, ensuring funds are only disbursed when milestone attestations are cryptographically verified .
	•	VotingContract (Governance): Also a Soroban smart contract, it mints and tracks Soulbound Tokens (SBTs) for membership and fungible tokens for proportional voting power . It handles proposal creation, delegation logic, and on-chain quorum tallies .
B. Integration Track Partners Our FaaS API Gateway connects B2B clients to the following ecosystem partners :
	•	MoneyGram Access (Fiat On/Off-Ramp): Integrated into the Remittance Orchestrator service . When an end-user contributes via a B2B client's app (e.g., Amero), the Escala API calls the MoneyGram Access API to seamlessly convert local fiat into USDC for the Soroban TreasuryContract .
	•	Circle (USDC Liquidity): Used as the underlying stablecoin for all community funds, guaranteeing 1:1 value preservation for diaspora remittances before they are deployed to local projects .
	•	Stellar Disbursement Platform (SDP): Used as the core off-ramp orchestration engine. Once Soroban smart contracts release funds, Escala’s API triggers the SDP to handle the automated, milestone-based bulk payouts to local suppliers, closing the loop from fiat-in to fiat/USDC-out.

Common Headers (Multi-Tenant Architecture)
To support our B2B FaaS model, all API requests must include standard authentication and tenant identification headers:
	•	Authorization: Bearer <JWT>
	•	Content-Type: application/json
	•	X-Idempotency-Key: <uuid> (Required for state-changing financial endpoints)
	•	X-Tenant-ID: <client_api_key> (Identifies the specific NGO, Cooperative, or App making the request)

Security & Architecture Guidelines
	•	Authentication & Enterprise Identity (OIDC): To ensure secure multi-tenant B2B access for NGOs and cooperatives, the architecture utilizes Firebase Authentication (Google Cloud Identity Platform) as our strict OIDC (OpenID Connect) provider. Firebase natively handles the OIDC standard, issuing secure JWTs for tenant sessions, managing MFA, and seamlessly integrating with our GCP-hosted middleware without building custom identity rails. 
	•	Key Management: Preference for non-custodial wallets via Stellar Wallets Kit; HSM architecture for custodial B2B tenant users.
	•	Hybrid Auditability: On-chain events (Soroban) merged with off-chain logs (ElasticSearch) for regulatory reporting.
	•	Encryption: TLS in transit and AES-256 at rest for all PII data.
	•	Idempotency: Strict enforcement of idempotency keys to prevent double-spending or duplicate token minting during network retries.
