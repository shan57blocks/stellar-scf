1. Executive Summary
ChimpDAO is building a physical wallet card for Stellar.
The product combines a secure NFC card, a native iOS app, Soroban smart contracts, and Stellar-native protocol integrations to create a hardware-secured wallet experience. Users will be able to activate a physical card, fund a card-linked Stellar account, view balances, authorize actions by tapping the card, swap assets, and access DeFi strategies through a simple mobile interface.
The card uses the familiar form factor of a bank card, but it is not a debit card, credit card, prepaid card, payment card issuer product, custodial wallet, or fiat payment service. Technically, the card acts as a hardware-secured signer for Stellar actions.
ChimpDAO’s goal is to make Stellar feel tangible and accessible:
As familiar as tapping a card, as powerful as a programmable Stellar wallet.
For this SCF Build Integration Track submission, the core integrations are:
* DeFindex as the primary yield strategy integration.
* Soroswap for asset conversion and routing.
* Stellar Wallets Kit-compatible flows for onboarding and wallet interoperability.
* Blend support where relevant, either through DeFindex strategies or a limited direct lending-market proof of concept.
The project is iOS-only for this grant. Android support may be explored later but is not part of the funded scope.

2. Product Definition
2.1 What ChimpDAO Card Wallet Is
ChimpDAO Card Wallet is a non-custodial physical wallet interface for Stellar.
It consists of:
* A secure NFC card.
* A native iOS application.
* Soroban smart contracts.
* A card-linked Stellar account / smart wallet model.
* Stellar RPC transaction preparation and submission.
* Integrations with Stellar DeFi and wallet infrastructure.
The card signs action-specific authorization payloads. The iOS app prepares transactions and displays the user interface. Soroban contracts verify permissions and execute card-linked logic. External protocols such as DeFindex, Soroswap, and Blend provide the DeFi functionality.
2.2 What ChimpDAO Card Wallet Is Not
ChimpDAO is not building:
* A regulated payment card.
* A debit card or credit card.
* A prepaid card.
* A custodial wallet.
* A bank account.
* A fiat on/off-ramp.
* A merchant payment processor.
* A remittance product.
* A regulated investment product.
* A yield guarantee.
* A financial advice service.
ChimpDAO will not custody user funds, operate fiat rails, issue payment instruments, process merchant payments, or provide investment advice.
The product is a wallet interface and hardware-backed authorization layer for Stellar-native assets and protocols.

3. Existing ChimpDAO Infrastructure
ChimpDAO already has a working technical foundation linking physical objects to on-chain Stellar ownership.
The current ChimpDAO system uses secure NFC chips embedded in physical merchandise. Each chip can generate and store a private key directly on the hardware. The private key remains inside the chip and is not exposed to the mobile app. The chip signs messages through NFC/APDU commands, and Soroban smart contracts verify those signatures to authorize ownership-related actions.
The existing implementation includes:
* Secure NFC chip sourcing and validation.
* Native iOS NFC/APDU communication.
* Chip-generated keys.
* Hardware-backed message signing.
* SEP-53-inspired authentication.
* Soroban smart contracts.
* Claim and transfer flows.
* Physical-object-linked NFTs.
* Ownership verification through Stellar.
* A public website.
* Open-source repositories for contracts and iOS.
This validates the core primitive required for ChimpDAO Card Wallet:
Physical object
→ secure NFC chip
→ hardware-generated private key
→ action-specific signature
→ Soroban verification
→ Stellar ownership or transaction authorization
The grant extends this validated primitive from physical merchandise authentication into a broader physical wallet card for Stellar assets and DeFi.

6. Proposed Account Model
ChimpDAO Card Wallet will use a card-linked account architecture.
The preferred model is a Soroban smart wallet / contract account model where the physical card acts as an authorized hardware signer. This allows the card-linked wallet to hold Stellar assets and interact with Stellar contracts while enforcing custom authorization rules.
The final implementation may use one of two closely related patterns, depending on implementation constraints discovered during Tranche 1:
Option A - Card-Linked Contract Account
The card-linked wallet is a Soroban contract account.
The contract account can hold assets and enforce authorization using custom logic. The physical card public key is registered as an authorized signer. Sensitive actions require a valid card-backed signature.
This is the preferred long-term model because it aligns with smart wallet patterns and allows programmable authorization.
Option B - Card Registry + Controlled User Account
The user’s Stellar account remains the primary asset-holding account, while a Soroban CardRegistry and authorization layer verifies card-backed signatures before allowing specific contract actions.
This model may be used for specific flows where direct contract account behavior is not optimal or where protocol integrations require a simpler account pattern.
6.1 Account Layers
The system distinguishes four account layers:
1. External User Wallet
An external Stellar wallet used for onboarding, funding, or interoperability.
Examples:
* Freighter-compatible wallet.
* Wallets Kit-supported wallet.
* Mobile deep-link wallet flow.
* WalletConnect-compatible flow where feasible.
The external wallet is not required to be the main ChimpDAO wallet, but it can help users fund or connect their card wallet.
2. Card-Linked Smart Wallet
The primary ChimpDAO wallet account.
This is the account controlled by the physical card authorization model. It can hold Stellar assets, interact with Soroban contracts, and execute supported DeFi actions.
3. Transaction Submitter / Fee Payer
A transaction source account may be used to submit transactions to the Stellar network.
Depending on final implementation, this can be:
* The user’s account.
* The card-linked wallet account.
* A submitter/channel account.
* A sponsored-fee account, if implemented.
The submitter does not custody user funds.
4. Protocol Accounts and Contracts
External ecosystem protocols remain independent.
These include:
* DeFindex vault contracts.
* Soroswap router contracts and routing services.
* Blend pools.
* Stellar asset contracts.
* Token contracts.
* External wallets.
ChimpDAO prepares and authorizes interactions with these protocols but does not replace them.

8. Hardware Security Model
8.1 Secure NFC Card
The ChimpDAO card contains a secure chip capable of generating and storing private keys directly on the hardware.
The chip is responsible for:
* Generating a key pair.
* Storing the private key.
* Exposing or deriving the public key.
* Signing action-specific payloads.
* Keeping the private key non-extractable.
* Communicating with the iOS app through NFC/APDU.
The card is treated as a hardware signer.
8.2 Key Slots
The existing ChimpDAO implementation uses a specific key slot for chip-generated keys. The card wallet design will continue using a deterministic and documented key slot strategy.
Potential key usage:
* Slot 1: primary card wallet signer.
* Additional slots: future expansion for secondary identities, recovery, limited-use authorizations, or multi-purpose card profiles.
* Slot 0: not used for externally loaded keys unless a future architecture decision explicitly requires it.
For this grant, the primary goal is to use one secure hardware-generated key as the card’s main signing identity.
8.3 NFC/APDU Communication
The iOS app communicates with the chip through NFC/APDU commands.
The app does not receive the private key. It sends a signing request to the card. The card returns a signature. The app includes that signature in the transaction authorization flow.
8.4 Physical Possession Requirement
Sensitive actions require the user to tap the physical card.
This creates a physical possession requirement for key actions such as:
* Activation.
* Transfers.
* DeFi deposits.
* DeFi withdrawals.
* Permission changes.
* Recovery or revocation actions where supported.

9. Authorization Model
The ChimpDAO authorization model is action-specific.
The card does not sign generic approvals. It signs a structured payload describing one exact action.
Examples of action types:
ACTIVATE_CARD
ASSOCIATE_EXTERNAL_WALLET
TRANSFER_ASSET
EXECUTE_SOROSWAP
DEPOSIT_DEFINDEX
WITHDRAW_DEFINDEX
SET_LIMIT
LOCK_CARD
REVOKE_CARD
Each action payload includes enough context to prevent misuse.
9.1 Canonical Payload Fields
A representative payload contains:
network_passphrase
contract_id
card_id
card_public_key
card_account_id
action_type
source_account
target_contract
target_function
asset_identifier
asset_issuer_or_contract
amount
destination
strategy_or_pool_id
route_hash
min_amount_out
max_slippage_bps
nonce
expiration_ledger
chain_context
Not every field is used for every action, but every action must be deterministic and explicit.
9.2 Signature Verification Rules
A signature is accepted only if:
* It is produced by the registered card public key.
* The card is active.
* The card is not revoked.
* The nonce has not been used.
* The expiration ledger has not passed.
* The payload matches the requested action.
* The target contract is allowed.
* The asset is supported.
* The amount respects the policy.
* The network passphrase matches the target network.
* The contract ID matches the expected contract.
* The signature cannot be reused for another action.
9.3 Replay Protection
Replay protection is enforced through:
* Nonces.
* Expiration ledgers.
* Action-specific payloads.
* Contract ID binding.
* Network passphrase binding.
* Target contract binding.
* Optional monotonic nonce sequence per card.
9.4 Smart Wallet Authorization
The preferred architecture uses a smart wallet / contract account pattern.
The card-linked smart wallet can implement custom authorization logic. This may rely on a __check_auth-style authorization flow or an equivalent explicit contract-level verification flow depending on final implementation constraints.
The key concept is:
No card-backed signature
→ no sensitive card-linked action

15. Stellar RPC Transaction Lifecycle
For every Soroban interaction, the iOS app follows a structured transaction lifecycle.
  



Detailed lifecycle:
1. User selects an action.
2. The app builds a contract invocation.
3. The app builds an action-specific card authorization payload.
4. The app requests a signature from the secure NFC card.
5. The card signs the payload and returns the signature.
6. The app creates the Soroban transaction.
7. The app simulates the transaction through Stellar RPC.
8. The app receives required ledger footprint, resource fees, and authorization data.
9. The app assembles the transaction.
10. The app signs the transaction with the required transaction source account.
11. The app submits the transaction.
12. The app polls transaction status.
13. The app updates balances, positions, or error states.
This lifecycle applies to:
* Card activation.
* External wallet association.
* Transfers.
* Soroswap conversions.
* DeFindex deposits.
* DeFindex withdrawals.
* Blend actions if implemented.
* Policy updates.
* Recovery actions.

17. Soroswap Integration Design
Soroswap is used for asset conversion and routing.
The goal is to reduce friction when a user holds one asset but needs another asset for a supported action.
17.1 Example Use Case
A user holds XLM but wants to deposit USDC into a DeFindex strategy.
ChimpDAO should allow:
XLM balance
→ quote route through Soroswap
→ review swap
→ tap card
→ receive USDC
→ deposit into DeFindex
Depending on transaction complexity, the swap and deposit may be:
* A single composed transaction, if feasible.
* A guided two-step flow: swap first, then deposit.
* A staged flow where the app tracks both actions.
17.2 Soroswap Payload Context
A Soroswap payload should include:
action_type = EXECUTE_SOROSWAP
card_account_id
asset_in
asset_out
amount_in
min_amount_out
route_hash
max_slippage_bps
router_contract
nonce
expiration_ledger
network_passphrase
contract_id
17.3 Route Integrity
The route displayed to the user must match the route signed by the card.
To prevent route manipulation:
* The route or route hash is included in the signed payload.
* The minimum amount out is included in the signed payload.
* The slippage value is included in the signed payload.
* The asset in and asset out are included in the signed payload.
* The router or target contract is included in the signed payload.
17.4 Soroswap Verification Criteria
Completion is verifiable when:
* The app can fetch or construct a supported swap route.
* The app displays quote, slippage, and expected output.
* The card signs a route-bound payload.
* The swap succeeds on testnet and/or mainnet.
* Transaction examples are documented.

18. Blend Support Design
Blend is a secondary DeFi integration.
The preferred approach is to support Blend through DeFindex strategies when available. This keeps the user experience focused and avoids fragmenting the product.
If feasible within scope, ChimpDAO may also implement a limited direct Blend proof of concept.
18.1 Blend Through DeFindex
This is the preferred path.
Flow:
Card-linked asset
→ DeFindex strategy
→ strategy has Blend exposure
→ user sees position through ChimpDAO
This allows ChimpDAO to support Blend exposure without building a full standalone Blend interface during this grant.
18.2 Direct Blend Proof of Concept
A direct proof of concept may include:
* Reading selected Blend pool data.
* Displaying lending market information.
* Preparing one limited supply or withdraw action.
* Requiring card-backed authorization.
* Documenting transaction examples.
18.3 Blend Verification Criteria
Completion is verifiable through either:
* A DeFindex strategy using Blend exposure displayed in the ChimpDAO app.
* Or a direct limited Blend action successfully executed and documented.

23. Security Threat Model
23.1 Threat: Replay Attack
An attacker tries to reuse a valid card signature.
Mitigations:
* Nonce per card.
* Expiration ledger.
* Action-specific payload.
* Contract ID binding.
* Target contract binding.
* Network passphrase binding.
* Nonce consumption on successful use.
23.2 Threat: Signature Reuse for Different Action
A signature for one action is reused for another.
Mitigations:
* Include action type in payload.
* Include target contract.
* Include function name.
* Include asset.
* Include amount.
* Include destination or strategy ID.
* Contract verifies exact action context.
23.3 Threat: Route Manipulation
A swap route is changed after user approval.
Mitigations:
* Include route hash in signed payload.
* Include asset in and asset out.
* Include min amount out.
* Include max slippage.
* Include router contract.
* Display route summary before signing.
23.4 Threat: Malicious Protocol Call
A malicious target contract is inserted into a transaction.
Mitigations:
* PolicyManager protocol allowlist.
* Signed target contract.
* Signed function name.
* App-side review screen.
* Contract-side verification.
23.5 Threat: Lost Card
A user loses their physical card.
Mitigations:
* Emergency lock.
* Optional external wallet association.
* Revocation flow.
* Future recovery module.
* Limits on high-risk actions where implemented.
23.6 Threat: Stolen Card
A card is stolen and used by someone else.
Mitigations:
* Optional app-level authentication.
* Optional transaction limits.
* Optional external wallet co-approval for high-risk actions.
* Emergency lock.
* Revocation flow.
* Clear user education.
23.7 Threat: Compromised iOS App
A compromised app tries to make the card sign malicious actions.
Mitigations:
* Action-specific payload display.
* Signed payload includes exact action.
* Contract-side policy checks.
* Protocol allowlist.
* Amount and destination binding.
* Optional limits.
* User-visible transaction review.
23.8 Threat: Compromised Backend
ChimpDAO should minimize backend dependency.
Mitigations:
* Critical authorization verified on-chain.
* No backend custody.
* Public contract addresses.
* Public transaction verification.
* Prefer client-side transaction preparation where feasible.
* Any API response used for quotes/routes must be bound to signed payloads.

32. Summary
ChimpDAO Card Wallet is an iOS-first physical wallet card for Stellar.
It builds on ChimpDAO’s existing NFC-authenticated merchandise infrastructure and extends it into a wallet architecture for Stellar assets and DeFi.
The secure NFC card acts as a hardware-backed signer. The iOS app provides the wallet interface. Soroban smart contracts manage card-linked identity, authorization, policy, and protocol routing. Stellar RPC powers transaction simulation and submission. DeFindex, Soroswap, Blend, and Stellar Wallets Kit-compatible flows connect the product to existing ecosystem building blocks.
The final result is a bank-card-like user experience without becoming a regulated payment card:
A non-custodial, hardware-secured physical wallet card for Stellar assets, DeFi, and future real-world utility.
